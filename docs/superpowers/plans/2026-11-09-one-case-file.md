# ملف حالة واحد لكل أسرة — خطة التنفيذ

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** تحويل تسجيل الأسرة والحالة إلى ملف حالة واحد بكود ثابت، مع نقل كل الروابط الحالية بأمان وإزالة اسم الأسرة من تجربة الموظف.

**Architecture:** يظل معرّف سجل الأسرة الحالي والكود الفريد هما هوية الملف حتى لا تتغير روابط الكفالات والأفراد. تنتقل التصنيفات وسجلات الملاحظات والمرفقات إلى علاقات مباشرة بالملف، وتُحفظ الجداول القديمة كأرشيف مقيد مع خريطة للروابط القديمة. تستخدم صفحات التطبيق نوع `CaseFile` واحداً وخدمات موحدة.

**Tech Stack:** React، TypeScript، Supabase PostgreSQL وRLS، Cloudflare Pages Functions، Vitest، pgTAP.

**Spec:** `docs/superpowers/specs/2026-11-09-one-case-file-design.md`

## Global Constraints

- «كل أسرة تبقى ملف حالة واحد بكودها».
- «اسم الأب اختياري، واسم الأم مطلوب» للملفات الجديدة؛ الملف القديم الناقص لا يمنع ترحيله.
- «لا يدمج ملفين تلقائياً ولا يغيّر الأكواد أو روابط الأطفال والكفالات».
- تُحفظ ملاحظات كل سجل قديم بمعرّفه وتاريخه، وتبقى مسارات المرفقات وملفات Storage والنصوص المستخرجة.
- الجداول القديمة «في أرشيف لا يستطيع الموظفون قراءته أو تعديله؛ لا تُحذف تلقائياً في هذا الإصدار».
- تستمر صلاحيات القراءة والكتابة الحالية؛ المساعد يظل مقيداً بصلاحية الموظف.
- لا نشر للواجهة التي تعتمد على البنية الجديدة قبل نجاح ترحيل Supabase المتصل والتحقق منه.

## Review Focus

- ملف قديم بلا اسم أم يظل قابلاً للعرض، بينما إنشاء ملف جديد يطلب الاسم؛ اختبر الاثنين في Task 3.
- أسرة لها عدة سجلات حالة قديمة تخرج بملف واحد، وتصنيفات غير مكررة، وملاحظات مؤرخة محفوظة؛ اختبر النقل في Task 1.
- أسماء أو أرقام متطابقة لا تدمج أسراً ولا تنقل بيانات بين الأكواد؛ اختبر تقرير المراجعة في Task 1.
- مرفق قديم بمسار لا يبدأ بكود الأسرة يظل قابلاً للتنزيل، والملفات الجديدة لا تصبح عامة؛ اختبر سياسة المرفقات في Task 1 ورفع/تنزيل الملف في Task 4.
- رابط قديم بمعرّف حالة يفتح ملف الأسرة المقابل؛ اختبر خريطة الروابط في Task 1 وRoute في Task 3.
