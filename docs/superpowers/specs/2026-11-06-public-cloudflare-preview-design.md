# معاينة عامة للنظام عبر GitHub وCloudflare Pages

## الهدف

إتاحة نسخة أونلاين يقدر صاحب المشروع وفريقه يجربوها من المتصفح، مع استخدام بيانات تجريبية فقط.

## التصميم المختار

- GitHub يحفظ الكود ويشغّل تحديث المعاينة عند رفع تغييرات لفرع مخصص للتجربة.
- Cloudflare Pages يستضيف الواجهة ووظائف الخادم. رابط المعاينة عام كما طلب صاحب المشروع.
- Supabase الذي أنشأه صاحب المشروع يوفر تسجيل الدخول وقاعدة البيانات وتخزين المرفقات. نطبّق عليه ترحيلات المشروع، وننشئ حساب المدير العام الأول بعد ذلك.
- يظل Workers AI على Cloudflare كما هو في إعداد المشروع. مفاتيح Supabase السرية تضاف في إعداد Cloudflare فقط، ولا توضع في GitHub أو الكود.
- تستخدم المعاينة أسماء وملفات وهمية. لا تضاف بيانات أسر حقيقية أو حسابات موظفين حقيقيين.

## البدائل التي دُرست

- GitHub Pages: غير مناسب؛ يستضيف ملفات ثابتة ولا يشغّل وظائف الدخول والملفات.
- GitHub Actions لنشر Cloudflare Pages: ممكن، لكنه يحتاج رمز Cloudflare سرياً وإدارة خطوات نشر إضافية. تكامل GitHub المدمج في Cloudflare أبسط لهذا المشروع.
- النشر اليدوي: ممكن، لكنه لا يحدّث المعاينة تلقائياً بعد تغييرات الكود.

## الحدود والمخاطر

- الرابط عام ويمكن لأي شخص فتح واجهة الدخول. السجلات تبقى محمية بتسجيل الدخول وصلاحيات قاعدة البيانات؛ وجود رابط عام لا يجعل بيانات الأسر عامة.
- اختيار فرع تجربة منفصل يمنع إرسال تغييرات المعاينة مباشرة إلى فرع الإصدار الرئيسي.
- لا نربط مشروع إنتاج ولا نشغّل ترحيلات على قاعدة حقيقية. يجب التأكد من أن مشروع Supabase مخصص للاختبار قبل تطبيق الترحيلات.
- إعداد عنوان الموقع وروابط الرجوع لتسجيل الدخول في Supabase وCloudflare جزء من خطوات الربط.
- الأمان والتجربة يعتمدَان على ضبط المفاتيح والروابط والصلاحيات في الحسابات؛ لا يمكن تأكيد ذلك قبل اختبار الرابط المنشور.

## المطلوب بعد الموافقة

إعداد فرع التجربة وربط GitHub بـCloudflare Pages، إضافة متغيرات Supabase السرية في إعداد Cloudflare، تطبيق الترحيلات على مشروع الاختبار، إنشاء أول مدير عام، ثم تجربة الدخول والحالات والمرفقات والتبرعات على الرابط العام. لا نضع أي مفتاح في المحادثة أو المستودع.
