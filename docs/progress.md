# تقدم الشغل

## ٥ نوفمبر ٢٠٢٦ — تجربة النظام الجاهز ومقترح التصميم

- جرّبنا CiviCRM محلياً ببيانات وهمية فقط.
- النتيجة: الدخول والتبرعات يعملان؛ الحالات تحتاج إعداداً إضافياً؛ واجهة الدخول الافتراضية إنجليزية؛ والجلسة الافتراضية تنتهي مع جلسة المتصفح. لم نتحقق بعد من معاينة المرفقات داخل ملف الحالة.
- حسب تفضيل صاحب المشروع، المقترح الحالي هو واجهة مخصصة مع Supabase وCloudflare، والاستفادة من مكتبات مفتوحة المصدر عند الحاجة.
- أُزيلت حاويات وبيانات التجربة المؤقتة. لم تتغير ملفات التطبيق.
- أنشأنا [تقييم CiviCRM](evaluation/civicrm.md) و[مقترح التصميم](superpowers/specs/2026-11-05-charitable-case-system-design.md).
- اعتمد صاحب المشروع الاتجاه العام في ٥ نوفمبر ٢٠٢٦.
- أكد صاحب المشروع متابعة دفعات الكفالة الشهرية؛ أُضيف ذلك إلى التصميم.
- حدد صاحب المشروع أدوار المدير العام والمدير والموظف وصلاحيات قابلة للتغيير للموظف؛ أُضيفت للتصميم.
- أكد صاحب المشروع أن المساعد يلتزم بصلاحيات الموظف الذي يستخدمه؛ أُضيف ذلك للتصميم.
- قبل بناء المساعد، نختار بين Cloudflare Workers AI وGoogle Gemini بعد مراجعة الشروط وحدود الاستخدام.
- طلب صاحب المشروع كوداً سهلاً وفريداً لكل أسرة، مثل `F-0001`؛ أُضيف للتصميم والخطة، ويُولّد من قاعدة البيانات لمنع التكرار.
- طلب استخراج النص العربي والحقول المطلوبة من الصور وملفات PDF، بما فيها ملفات PDF المصورة، مع مراجعة الموظف قبل الحفظ؛ أُضيف للتصميم.
- أُعدت خطة التنفيذ في `docs/superpowers/plans/2026-11-05-charitable-case-system.md` للمراجعة.
- راجعنا الخطة للتأكد من تغطية المتطلبات والاختبارات؛ التنفيذ لم يبدأ بعد، وننتظر مراجعة الخطة واختيار طريقة التنفيذ.
- اتفق صاحب المشروع على تنفيذ الخطة بمساعدين مع مراجعة كل جزء. حدّثنا حدّ الانتهاء: تجهيز ملفات النشر فقط دون نشر أو ربط خدمة إنتاجية، مع بيانات وهمية واختبارات محلية.

## ٥ نوفمبر ٢٠٢٦ — الخطوة ١: شكل التطبيق العربي

- جهّزنا React وTypeScript وVite، مع اسم «نظام الجمعية»، واتجاه من اليمين للشمال وقائمة مناسبة للموبايل.
- أضفنا مسار الدخول ومسارات مؤقتة للرئيسية والأسر والحالات والتبرعات والكفالات والمساعد والموظفين. من غير جلسة بتظهر رسالة تطلب تسجيل الدخول؛ شاشة الدخول نفسها لسه مؤقتة.
- كتبنا اختبارات الشكل والمسارات قبل التنفيذ. أول تشغيل فشل لأن `AppShell` مش موجود، وبعد التنفيذ نجحوا ٩ اختبارات.
- نجح `npm run test` و`npm run typecheck` و`npm run build`. نجح اختبار Playwright على Chromium محلي بعرض ٣٦٠ بكسل: مفيش تمرير أفقي، وروابط القائمة ظاهرة وارتفاعها ٤٤ بكسل على الأقل، والتنقل بالكيبورد شغال.
- جهّزنا أوامر `test` و`test:worker` و`test:e2e` و`typecheck` و`build`. أمر Worker بيخرج بنجاح من غير اختبارات حالياً؛ إضافة اختبارات الخدمات مطلوبة في الخطوات الجاية.
- ما اتوصلناش بأي خدمة خارجية، وما استخدمناش بيانات حقيقية أو مفاتيح، وما نشرناش التطبيق.
- الخطوة الجاية: دخول الموظفين والجلسات والصلاحيات وفحص سياسات قاعدة البيانات. حماية واجهة المسارات وحدها مش بديل عن صلاحيات الخادم وقاعدة البيانات.
- متطلبات الخطة ثابتة: كود الأسرة فريد وثابت من قاعدة البيانات، ونتائج OCR اقتراحات بتتراجع قبل الحفظ، والمساعد والملفات ملتزمين بصلاحيات الموظف. الخطوة دي ما نفذتش المزايا دي.

## ٥ نوفمبر ٢٠٢٦ — الخطوة ٢: دخول الموظفين وحدود الصلاحيات

- أضفنا شاشة دخول بالكود وكلمة السر، وحفظ جلسة Supabase بين إعادة التحميل، ومسارات واجهة تراعي صلاحيات الموظف.
- أنشأنا الموظفين والصلاحيات وربط Auth الخاص وسجل تغييرات الوصول. المدير ينشئ موظفين فقط؛ المدير العام وحده يعطّل الوصول، مع بقاء السجل والتاريخ.
- وظائف Pages تتحقق من الجلسة على الخادم. قاعدة البيانات تمنع التصعيد والكتابة المباشرة وتتحقق من الدور مرة ثانية عند كل تعديل حساس.
- حددنا الجلسة ب٣٠ يوماً من أول دخول؛ تحديث الرمز لا يمدّها. الخروج يلغي وصول الرمز الحالي فوراً من خلال سجل إلغاء تفحصه السياسات، ثم يلغي refresh token في Auth.
- أضفنا رسائل دخول عامة وحد محاولات ذرّياً لكل كود وعنوان، وفصلنا مفاتيح الخادم عن إعداد المتصفح. البريد العشوائي لحساب Auth لا يحتوي كود الموظف أو اسمه.
- اختبارات الصلاحيات وشاشة الدخول بدأت بفشل موثق ثم نجحت. نجحت اختبارات قاعدة البيانات على Supabase محلي، ومنها قراءة وإضافة وتعديل صفوف حالات وتبرعات تجريبية تحت RLS، وحد الشهر والتعطيل والخروج. نجحت اختبارات Auth/API مع GoTrue وPostgREST المحليين.
- جداول الحالات والتبرعات الحقيقية ما زالت ضمن الخطوات التالية؛ لازم تطبّق نفس دوال السياسات ونختبرها على الجداول النهائية. [نموذج البيانات](data-model.md) يوثّق التعاقد وخطوات أول حساب واستعادة الدخول.
- التحقق النهائي: ٢٢ اختبار واجهة وخدمة متصفح، ١١ اختبار API محلي، ٣٤ اختبار SQL، وفحص TypeScript وبناء Vite وPages Functions واختبار Chromium للموبايل. لا نشر ولا ربط إنتاجي ولا بيانات حقيقية.

## ٦ نوفمبر ٢٠٢٦ — الخطوة ٣: الأسر والحالات

- أضفنا سجلات الأسر وأفرادها والحالات وتصنيفاتها الستة، مع بحث عربي لا يغيّر الأسماء المحفوظة وهاتف اختياري.
- تولّد قاعدة البيانات أكواداً ثابتة وفريدة من تسلسل، وتمنع صلاحيات التطبيق تغيير الكود أو حذف الأسرة. اختبرنا ٢٠ طلباً متزامناً ببيانات وهمية.
- طبقنا سياسات الجلسة وصلاحيات الحالات على الجداول الفعلية، وحفظ الحالة والتصنيفات وإضافة فرد للأسرة ذريّان.
- أضفنا صفحات إنشاء وبحث وتعديل الأسرة والحالة وعرض أفراد الأسرة. الاختبارات والبيانات محلية ووهمية فقط؛ لم نربط إنتاجاً أو ننشر.

## ٦ نوفمبر ٢٠٢٦ — الخطوة ٤: مرفقات الحالات واستخراج النص

- أضفنا مرفقات خاصة للحالة، معاينة الصور وPDF، ورفع الملفات بعد حفظ الحالة. يتحقق التخزين والبيانات من صلاحيات الحالات والجلسة؛ أسماء التخزين عشوائية.
- أضفنا استخراج النص العربي محلياً من نص PDF والصور وصفحات PDF المصورة، مع مراجعة ونسخ يدويين دون حفظ النص تلقائياً. الحد ٢٠ ميجابايت و٢٠ صفحة للملف؛ دقة الاستخراج وترتيب النص يعتمدان على المستند.
- اختبرنا بملفات عربية وهمية وSupabase محلي فقط. يُفرض حد صفحات PDF في مسار رفع موثوق على الخادم، وتُمنع الكتابة المباشرة للمرفقات. تفاصيل الاختبارات والقيود في تقرير الخطوة.

- اقتراح قيم الحقول يقع ضمن الخطوة ٦: يجب التحقق من صلاحية الموظف ومراجعته وتأكيده الصريح لكل قيمة قبل تطبيقها وقبل الحفظ في مراجعة الخطوة والختام.


## ٦ نوفمبر ٢٠٢٦ — الخطوة ٥: التبرعات والكفالات

- أضفنا المتبرعين والتبرعات النقدية والعينية بأنواعها الثلاثة عشر، مع مبلغ بالجنيه المصري أو كمية ووحدة ووصف للأصناف.
- أضفنا ربط الكفالة بمتبرع وأسرة، واستحقاقاً منفصلاً وفريداً لكل شهر، وتسجيل تاريخ ومبلغ الاستلام. يوم البداية هو يوم الاستحقاق، مع آخر يوم للشهر الأقصر، والبداية والنهاية مشمولتان. الدفعة المستلمة لا تظهر متأخرة.
- النهاية تمنع الأقساط التالية وتحذف غير المستلم منها، ولا يمكن جعلها قبل قسط مستلم. جدول الكفالة وأطرافها ثابتة لحماية التاريخ؛ تغييرها يحتاج كفالة جديدة. توليد الأقساط حتى نهاية الشهر حسب UTC يتم عند فتح/تحديث الصفحة لكل قارئ مخوّل بالتبرعات والحالات؛ لا يعتمد على زيارة كاتب أو مهمة مجدولة.
- التبرعات مستقلة عن الحالات. عرض وربط الكفالات يحتاج قراءة الحالات أيضاً لأن الكفالة تحتوي معرّف الأسرة؛ الكتابة تحتاج كتابة التبرعات وقراءة الحالات، دون كتابة الحالات. موظف التبرعات وحده لا يحصل على أسماء الأسر أو أكوادها أو معرّفاتها، وتوضح الواجهة طلب منح قراءة الحالات من المدير.
- طبقنا سياسات الجلسات وRLS على الجداول الفعلية الأربعة، واختبرنا الكاتب والقارئ وموظف الحالات فقط وانتهاء الجلسة. القوائم تجلب صفحات متتابعة تتجاوز حد ألف صف الافتراضي. اختبارات الوحدة وSQL وواجهة الكفالات بدأت بفشل ثم نجحت؛ تفاصيل التحقق والقيود في تقرير الخطوة ٥.
- البيانات والملفات محلية ووهمية فقط؛ لا اتصال إنتاجي أو نشر أو خدمة AI خارجية. لا حسابات كاملة أو مصروفات أو أرصدة أو تحويل عملة أو بوابة عامة للتبرع.


### مراجعة الخطوة ٥ — الجولة ١

- أصلحنا غياب الالتزامات الشهرية عن القرّاء: دالة محدودة تتحقق من قراءة التبرعات والحالات تُنشئ الأقساط المتوقعة غير المستلمة فقط عند العرض، دون منح القارئ تعديل الجداول أو الاستلامات أو المبالغ أو الأطراف. اختبرنا انتقال قارئ فقط بين يناير وفبراير ومارس دون زيارة كاتب.
- أصبحت الاستلامات المسجلة ثابتة في قاعدة البيانات؛ طلبات API المباشرة لمسحها أو تغييرها مرفوضة. تسجيل الاستلام ذري ومشروط ببقاء الدفعة غير مستلمة، مع تعارض واضح للطلب الخاسر عند التزامن. لا يوجد مسار لتصحيح استلام مسجل حالياً.
- أضفنا ترحيلاً لاحقاً `006_sponsorship_read_schedule_receipts.sql` واختبارات SQL وAPI محلية وواجهة. تفاصيل RED/GREEN والتحقق النهائي في تقرير الخطوة ٥.
